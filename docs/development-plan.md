# OLE-QS 線上題庫系統 — 開發計畫

> 版本：v1.0（初稿）
> 範圍：國中（108 課綱，第四學習階段）考古題影像 → 結構化題庫 → 線上檢索 → 自由組卷 → 輸出考卷

---

## 0. 專案定位與成功標準

### 0.1 一句話定義
把「一疊掃描的考古題圖檔」變成「可依課綱章節、題型、難度檢索，並在幾分鐘內組出一份完整考卷（含答案卷與詳解）」的系統。

### 0.2 核心使用者與情境
| 角色 | 主要情境 |
|---|---|
| 管理者 / 建置者 | 批次上傳題本掃描檔、監看擷取進度、管理課綱分類表 |
| 校對員（可能就是你） | 逐題檢查 AI 擷取結果、修正文字/公式/圖、確認分類標籤 |
| 教師（主要使用者） | 依「第X冊第Y章 + 難度 + 題型 + 題數」篩題 → 加入題籃 → 調整順序 → 匯出 PDF/Word |
| 學生（Phase 2 選配） | 線上作答自我練習、錯題本 |

### 0.3 成功標準（驗收指標）
- **擷取品質**：單選題文字+選項的完整正確率 ≥ 95%；含公式/圖形題 ≥ 85%（以人工校對前的原始輸出計算）。
- **校對效率**：校對員處理一題平均 ≤ 20 秒（純文字題）／≤ 45 秒（含圖或公式題）。
- **分類品質**：自動標註「章節」Top-1 準確率 ≥ 85%，Top-3 ≥ 95%。
- **組卷體驗**：教師從登入到匯出一份 25 題的段考卷 ≤ 5 分鐘。
- **題庫規模目標（第一階段）**：3,000 題可用題目、覆蓋國中五科七～九年級。

### 0.4 明確不做（第一版）
- 不做線上即時考試（監考、計時、防作弊）。
- 不做手寫作答的自動批改。
- 不做行動 App（響應式網頁即可）。
- 不做多國語系（介面固定繁體中文）。

## 1. 資料規格（先定義清楚，後面所有模組都依賴這份規格）

### 1.1 題目型態
| 代碼 | 名稱 | 說明 |
|---|---|---|
| `single` | 單選題 | 國中會考絕大多數 |
| `multiple` | 多選題 | 部分校內段考 |
| `tf` | 是非題 | |
| `fill` | 填充題 | 答案為短字串/數值 |
| `matching` | 配合題 | |
| `calc` | 計算/非選題 | 需詳解、人工評分 |
| `essay` | 問答/寫作 | 國文、英文作文 |
| `group` | 題組 | 共用題幹（閱讀測驗、實驗敘述），底下掛多個子題 |

### 1.2 一題的完整欄位
```jsonc
{
  "id": "q_01H...",
  "type": "single",
  "stem": "下列何者為酸性物質？其 pH 值 $x$ 滿足 $x < 7$……",  // Markdown + LaTeX
  "assets": [                                    // 題目中的圖
    { "key": "FIG1", "url": "s3://.../fig1.png", "bbox": [120, 340, 480, 620] }
  ],
  "options": [
    { "label": "A", "content": "小蘇打水" },
    { "label": "B", "content": "檸檬汁" }
  ],
  "answer": ["B"],
  "explanation": "檸檬汁含檸檬酸……",             // 詳解，可為空
  "difficulty": 2,                               // 1~5
  "score_hint": 4,                               // 原卷配分
  "source": {
    "doc_id": "doc_2024_cap_science",
    "exam_name": "113年國中教育會考",
    "subject": "自然",
    "year": 2024,
    "page": 3,
    "number_in_paper": 12
  },
  "tags": [
    { "node_id": "sci.chem.acid_base", "type": "curriculum", "primary": true,
      "confidence": 0.92, "labeled_by": "ai" }
  ],
  "status": "reviewed",       // draft | needs_review | reviewed | rejected
  "dup_cluster_id": "dc_0042"
}
```

**關鍵設計決定**
1. **題幹用 Markdown + LaTeX（`$...$`）儲存**，不存 HTML。前端用 KaTeX 渲染，匯出 PDF 與 Word 都從同一份來源產生，避免多套格式不同步。
2. **資產分兩類，不要一律裁圖**（PoC 實測：3 個資產中 2 個是表格）
   - `figure` → 裁成獨立 PNG，題幹用 `![](FIG1)` 佔位。適用數線圖、幾何圖、實驗裝置圖 —— 圖形本身即題意，無法文字化。
   - `table` → VLM 直接輸出 Markdown 表格，前端重繪。表格裁成圖片會失去三件事：組卷重排時無法縮放、無法全文檢索、匯出 Word 後老師不能改數字。理化科的表格比例更高，這個決定影響很大。
3. **題組用父子結構**：父題存共用題幹，子題存各自選項與答案。搜尋時以子題為單位，組卷時整組一起帶入。
4. **保留正規化前的原文**（`stem_raw`）。正規化（乘號、全形半形）方便搜尋與去重，但校對員需要能對照原圖逐字核對。

### 1.3 分類體系（Taxonomy）— 這是題庫的靈魂
採**雙軸**設計，因為老師的搜尋習慣和課綱編碼不一樣：

**軸一：課綱學習內容（權威、跨版本通用）**
```
自然 / 理化 / 物質的組成與特性 / Ja-IV-1 酸鹼鹽
數學 / 代數 / A-8-1 二元一次聯立方程式
社會 / 歷史 / 歷Ba-IV-2 台灣的原住民族
```

**軸二：教科書版本章節（老師實際使用的語言）**
```
康軒 / 理化 / 第4冊 / 第5章 酸鹼鹽 / 5-2 酸鹼中和
翰林 / 理化 / 第4冊 / 第4章 反應速率與化學平衡 / ...
```

兩軸之間建一張**對照表**（`curriculum_mapping`）。實作上：AI 只負責標軸一（課綱代碼），軸二由對照表推導。**這個決定很重要** — 否則每換一個版本就要重標一次全部題目。

**建置順序**：先做數學＋自然（分類邊界清楚、最好驗證），再做社會，最後做國文與英語（國文/英語的「章節」概念弱，改用能力向度：字音字形、閱讀理解、文法時態、字彙難度等）。

## 2. 系統架構

```
┌─────────────────────────────────────────────────────────┐
│  Web 前端  Next.js (App Router) + TypeScript             │
│  ├── 上傳與批次管理後台                                    │
│  ├── 校對工作台（左圖右表單，鍵盤流）  ← 使用率最高          │
│  ├── 題庫檢索 / 題目預覽（KaTeX）                          │
│  └── 組卷工作區 + 匯出                                     │
└──────────────┬──────────────────────────────────────────┘
               │ REST / JSON
┌──────────────▼──────────────────────────────────────────┐
│  API 服務  FastAPI (Python)                              │
│  auth / documents / questions / taxonomy / papers/export │
└──────┬───────────────────────────┬──────────────────────┘
       │ 任務入列                   │
┌──────▼─────────┐        ┌────────▼───────────────────────┐
│ Redis + Celery │        │ PostgreSQL 16                  │
│  擷取 Worker    │        │  + pgvector（去重/語意搜尋）     │
│  ├ 影像前處理    │        │  + pg_bigm（中文全文檢索）       │
│  ├ 版面偵測      │        └────────────────────────────────┘
│  ├ VLM 擷取     │        ┌────────────────────────────────┐
│  ├ 自動分類      │        │ 物件儲存 S3 / Cloudflare R2     │
│  └ 去重比對      │        │  原始掃描檔、裁切圖、匯出檔案      │
└────────────────┘        └────────────────────────────────┘
```

### 2.1 技術選型與理由
| 層 | 選擇 | 理由 |
|---|---|---|
| 前端 | Next.js + TypeScript + Tailwind + shadcn/ui | 校對工作台需要複雜互動；shadcn 省掉大量 UI 工 |
| 數學渲染 | KaTeX | 比 MathJax 快一個數量級，題庫列表要一次渲染數十題 |
| 後端 | FastAPI (Python) | OCR / 版面偵測 / 向量計算的生態全在 Python，不要為了語言統一而拆兩個服務 |
| 佇列 | Celery + Redis | 擷取是長任務（一頁數秒～數十秒），必須非同步 + 可重試 |
| 資料庫 | PostgreSQL + pgvector + pg_bigm | 一個 DB 同時處理關聯查詢、中文模糊搜尋、向量去重，不用另外架 ES |
| 儲存 | S3 相容（開發用 MinIO，正式用 R2） | 掃描檔量大、要 CDN |
| PDF 匯出 | HTML + KaTeX → Playwright 列印 | 與網頁預覽同一份渲染邏輯，所見即所得 |
| Word 匯出 | python-docx（公式先轉圖片） | 老師需要可再編輯的檔案；OMML 完美轉換成本過高，第一版妥協 |

> **可替代方案**：若你偏好全 TypeScript 單體，可用 Next.js + Prisma + BullMQ，把 VLM 擷取做成獨立的 Python 微服務。但版面偵測與影像前處理仍建議留在 Python。

## 3. 資料模型（PostgreSQL 概要）

```sql
-- 來源文件
source_document(id, title, exam_name, subject, year, grade, publisher,
                file_url, page_count, status, uploaded_by, created_at)
source_page(id, document_id, page_no, image_url, width, height,
            preprocessed_url, ocr_raw jsonb)

-- 題目
question(id, type, stem_md, stem_raw,      -- raw 為正規化前原文，供對照原圖
         answer jsonb, answer_status,      -- missing | ai_generated | verified
         explanation_md, difficulty,
         score, parent_id,                 -- 題組子題指向父題
         document_id, page_no,
         section_ord, number_in_section,   -- ⚠️ 題號分大題重編，唯一鍵是「大題+題號」
         status, extraction_confidence, dup_cluster_id,
         embedding vector(1024),           -- 去重 + 語意搜尋
         created_at, reviewed_by, reviewed_at)
question_option(id, question_id, label, content_md, ord)
question_asset(id, question_id, kind, url, markdown, bbox jsonb, ord)
   -- kind: figure（裁圖，url） | table（結構化，markdown） | chart
source_section(document_id, ord, name, type, score_rule, per_item_score, count)

-- 分類
taxonomy_node(id, parent_id, axis, subject, code, name, level, ord)
   -- axis: 'curriculum' | 'textbook'
question_tag(question_id, node_id, is_primary, confidence, labeled_by, created_at)
curriculum_mapping(curriculum_node_id, textbook_node_id, publisher)

-- 組卷
paper(id, title, owner_id, subject, total_score, layout_config jsonb,
      status, created_at)
paper_item(paper_id, question_id, ord, score, section_name)
paper_export(id, paper_id, format, url, include_answer, created_at)

-- 系統
app_user(id, email, name, role, created_at)   -- admin|editor|teacher|student
audit_log(id, actor_id, entity, entity_id, action, diff jsonb, created_at)
extraction_job(id, document_id, page_no, state, attempts, error, cost_usd, timings jsonb)
```

**索引重點**
- `question` 上建 `pg_bigm` GIN 索引於 `stem_md`（中文子字串搜尋）。
- `question.embedding` 建 HNSW 索引（去重與「找相似題」）。
- `question_tag(node_id, question_id)` 複合索引（依章節撈題是最高頻查詢）。

## 4. 核心模組 A：影像 → 結構化題目（最難、最該先做原型）

這是整個專案的技術風險集中處。**建議在寫任何 CRUD 之前，先花 3–5 天做一個純腳本的原型**，拿 20 張你的真實掃描檔跑通，量測正確率與單頁成本，再決定後續投入。

### 4.1 管線步驟
```
原圖 (JPG/PDF)
  ↓ ⓪ 截圖清理：偵測並裁掉手機截圖的 UI（導覽列、狀態列、灰底、頁面陰影）
  ↓ ① 前處理：去斜(deskew)、去雜訊、二值化增強、統一 DPI(300)
  ↓ ② 頁序還原：讀頁尾「【共 N 頁，第 M 頁…】」重排，不信任檔名順序
  ↓ ③ 版面切分：自動判斷欄數（段考卷多為單欄）；偵測圖框/表格 bbox
  ↓ ④ 資產處理：figure → 裁成 PNG 上傳 S3；table → 交由 VLM 輸出 Markdown 表格
  ↓ ⑤ VLM 擷取：把「頁影像 + 資產佔位資訊」送給視覺模型，
  ↓             要求輸出嚴格 JSON（大題、題號、題型、題幹 Markdown+LaTeX、選項、配分）
  ↓ ⑥ 結構驗證：配分總和 + 分大題題號連續性 + 選項數 + LaTeX 閉合（見 4.5）
  ↓ ⑦ 正規化：乘號 x/X/* → \times、全形半形統一（原文另存一份供對照）
  ↓ ⑧ 答案掛載：解析答案頁/答案卡，依「大題 + 題號」join
  ↓ ⑨ 去重比對：正規化文字 → embedding → 找既有相似題
  ↓ ⑩ 自動分類（見模組 B）
  ↓ ⑪ 標記信心度 → 寫入 status = needs_review
```

> 步驟 ⓪②④⑥⑦ 是 PoC #001 實測真實段考卷後補上的，詳見 [`poc-report-001.md`](poc-report-001.md)。

### 4.2 工具選型
| 步驟 | 主選 | 備援 / 交叉驗證 |
|---|---|---|
| 前處理 | OpenCV（deskew、CLAHE） | — |
| 版面／圖框偵測 | DocLayout-YOLO 或 PaddleOCR PP-StructureV2 | 手動框選（校對台補救） |
| 文字＋公式擷取 | 視覺語言模型（Claude / Gemini vision），輸出 Markdown+LaTeX | PaddleOCR 中文 OCR 做交叉比對，字元差異大時提高審查優先度 |
| 純數學公式 | 若 VLM 公式錯誤率偏高，加掛 Mathpix API 針對公式區塊 | — |

> **為何以 VLM 為主而非傳統 OCR**：傳統 OCR 只給你一串文字，題號、選項邊界、公式、上下標全要自己寫規則還原，中文考卷的版面變化極大，規則會爆炸。VLM 一次就能輸出結構化結果，且能理解「這是選項 (B)」這種語意。代價是成本與偶發幻覺 —— 所以第 ⑤ 步的結構驗證與第 4.4 節的人工校對不可省略。

### 4.3 擷取提示詞的輸出契約（節錄）
要求模型輸出嚴格 JSON、禁止解題、禁止補齊看不清楚的內容：

```jsonc
{
  "page_no": 3,
  "questions": [
    {
      "number": 12,
      "type": "single",
      "stem": "如圖 ![](FIG1) 所示，甲、乙兩物體……",
      "options": [{"label":"A","content":"..."}, ...],
      "figures_used": ["FIG1"],
      "confidence": 0.88,
      "uncertain_spans": ["第二行『甲』字模糊，可能為『申』"]
    }
  ],
  "notes": "本頁最後一題跨頁未完"
}
```
- **`uncertain_spans` 是關鍵欄位**：讓模型主動回報自己不確定的地方，校對台就能把游標直接定位過去，這比整題重讀快得多。
- **跨頁題目**：模型回報 `notes`，後處理階段把相鄰頁的殘題合併。
- **提示詞必須明令「逐字轉寫」**：不得修正錯字、不得規範化數學寫法、不得補齊看不清的內容。
  真實考卷會有誤植（PoC 樣本第 11 題「符合何條件」應為「符合此條件」），也會有 `(−8²)` 這種
  「負號不在括號內」的寫法 —— 模型會「好心」改成 `(−8)²`，但兩者意義完全不同。
  這是 VLM 最典型的幻覺型錯誤，且因為改得很合理而極難察覺。

### 4.5 結構驗證（零成本、零誤報的第一道防線）
在人工校對之前，先用純規則檢查考卷自身的內部一致性。已實作於 `scripts/validate_extraction.py`。

| 檢查 | 說明 |
|---|---|
| **配分總和** | 最強的訊號。台灣段考卷一定會印「每題 N 分，共 M 分」，漏抓/多抓/黏題都會讓總分對不上 |
| **分大題題號連續性** | ⚠️ 題號在每個大題**重新從 1 開始**，不可用全卷流水號檢查，否則全卷誤報 |
| 各大題題數與每題配分 | 與標題列宣告值比對 |
| 選項數與標籤 | 單選題應為 4 個、標籤不重複且遞增、內容不為空 |
| 題組子題配分合計 | 應等於題組總配分 |
| LaTeX `$` 成對 | 抓公式未閉合 |
| 資產完整性 | figure 有檔案、table 有結構化內容 |

注入故障測試（刪題 + 刪選項 + 破壞 LaTeX）確認三種錯誤皆能攔下。

### 4.4 校對工作台（人工在環，投資報酬率最高的一個畫面）
- **左右分割**：左側顯示原圖並自動捲動/高亮到當前題的 bbox；右側是可編輯表單。
- **鍵盤優先**：`Enter` 確認並跳下一題、`Ctrl+1~5` 設難度、`Ctrl+D` 標記重複、`Ctrl+R` 退回重跑。目標是雙手不離鍵盤。
- **即時 LaTeX 預覽**：輸入框下方即時 KaTeX 渲染。
- **信心度排序**：低信心題目排前面優先處理；高信心題目支援「批次快速確認」。
- **圖片補救**：可直接在左側原圖上拖框，重新裁切成 FIG。

## 5. 核心模組 B：課綱分類

### 5.1 流程
1. **先人工建立分類表**（不能讓 AI 自由發明標籤）。從教育部 108 課綱「學習內容」條目匯入，五科合計約 400–600 個節點。這是純資料整理工作，約 3–5 天。
2. **先用考卷的「範圍註記」縮小候選集合** 🎯
   段考卷的標題列幾乎都印著考試範圍，例如 PoC 樣本的
   「※請在答案卷作答（**範圍: 康軒版第一冊 1-1~1-4 p.71**）」。
   先擷取這行 `scope_note` 解析成候選章節集合，分類時只在該集合內選 —— 候選節點從「整個七年級數學」
   （數十節）縮到 **4 節**。準確率上升、prompt 變短、成本下降，三者同時改善。
   超出集合的題目標記為「疑似超出範圍」交人工確認（跨章節綜合題會落在這裡）。
3. **自動標註**：對每題送出「題目內容 + 候選節點清單（含代碼與描述）」，要求模型回傳 1 個主要標籤 + 至多 2 個次要標籤 + 信心度 + 判斷理由一句。
4. **難度自動預估**：以「題型 + 概念數 + 計算步驟數 + 是否跨章節」給 1–5 分初值，之後若有作答數據再用實際答對率校正。
5. **人工確認**：分類結果併入校對工作台同一畫面確認，不另開流程。
6. **版本章節推導**：透過 `curriculum_mapping` 自動產生康軒/翰林/南一的章節標籤。

### 5.2 品質控管
- 每累積 200 題抽樣 30 題人工複核，統計 Top-1 準確率，低於 85% 就補強候選節點的描述文字（通常是節點描述太抽象造成的）。
- 對於連續被人工改標的節點，記錄「易混淆對」，在提示詞中加入辨別說明。

## 6. 核心模組 C：題庫檢索

### 6.1 篩選面板
科目 → 版本/冊次/章節（或課綱代碼）→ 題型 → 難度區間 → 年份區間 → 來源考試 → 是否含圖 → 是否已有詳解 → 排除已用過的題。

### 6.2 搜尋
- **關鍵字**：pg_bigm 中文子字串（老師常搜「浮力」「歐姆定律」這種詞）。
- **相似題**：pgvector 餘弦相似度，用途是「我要這題的變化題」與去重。
- **結果呈現**：卡片式，直接渲染題幹與選項（可折疊答案），右上角「加入題籃」。

### 6.3 去重策略
1. 文字正規化：去空白、全形轉半形、移除題號與配分標記。
2. 精確重複：正規化後 SHA-256 完全相同 → 自動合併，保留最早來源，其他記為 `alias`。
3. 近似重複：embedding 相似度 > 0.93 → 進入 `duplicate_cluster` 待人工確認（數字改動的同型題要保留，換句話說的同一題要合併）。

## 7. 核心模組 D：組卷與匯出

### 7.1 兩種組卷模式
**A. 手動題籃（第一版必做）**
題庫瀏覽時逐題加入 → 題籃頁面拖曳排序、分節（一、單選題 二、填充題）、逐題配分、即時顯示總分與難度分布圖。

**B. 智慧組卷（第二版）**
輸入條件：章節權重（例：5-1 占 40%、5-2 占 60%）、題型配額、難度分布（易 3：中 5：難 2）、總題數、排除已出過的題 → 系統隨機抽樣並用約束求解調整 → 產生候選卷 → 可鎖定部分題目後「重抽其餘」。

### 7.2 排版與匯出
- **預覽即最終樣式**：網頁預覽用與 PDF 相同的列印 CSS（A4、雙欄、頁首校名/科目/班級座號欄、頁碼）。
- **PDF**：Playwright `page.pdf()`，中文字型內嵌（思源黑體/思源宋體）。
- **Word**：python-docx 產生 .docx；LaTeX 公式先用 KaTeX → SVG → PNG 內嵌為圖片（可正常列印，僅公式不可再編輯，第一版可接受）。
- **輸出三份**：試題卷、答案卷（僅答案表格）、教師詳解卷。
- **排版細節**（決定老師願不願意用）：題目不跨頁斷裂、圖片與題幹同頁、選項自動判斷單行/雙欄排列、答案卡格式可選。

## 10. 風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| 掃描品質差（歪斜、陰影、手寫註記） | 擷取正確率暴跌 | P0 就用最差的樣本測；建立「重掃建議」機制，品質分數過低的頁面直接退回 |
| 數學/化學式擷取錯誤 | 題目不可用 | 公式區塊獨立處理；校對台強制人工確認含公式題；必要時加掛專用公式 OCR |
| 圖形題比例高（自然、數學幾何） | 裁圖不準導致大量返工 | 版面偵測 + 校對台可手動重裁；圖多的科目排在後面做 |
| VLM 幻覺（自行「補完」看不清的字） | 錯題流入題庫且難以察覺 | 提示詞明令不得臆測、須回報 `uncertain_spans`；OCR 交叉比對；抽樣複核 |
| 分類標籤漂移 | 檢索找不到題 | 分類表為封閉集合，AI 只能選不能造；易混淆對持續累積說明 |
| 擷取成本失控 | 預算超支 | 每頁記錄 token 與費用於 `extraction_job`；先低成本模型初篩、低信心才升級模型重跑 |
| **版權** | 法律風險 | 教育會考/基測歷屆試題為公開資源，使用風險低；**各校段考卷、出版社模擬題與詳解有著作權疑慮**，建議：自建題庫僅收錄公開試題，或取得授權，或僅供內部教學使用不對外散布。這點建議在動工前先確認清楚 |

## 12. 待你確認的事項

1. **題目來源**：主要是歷屆會考/基測，還是也包含各校段考卷、坊間模擬題？（影響版權策略與版面多樣性）
2. **原圖格式**：整份 PDF、單頁掃描圖、還是手機拍攝？有無答案頁？答案是印在卷末還是另一張答案卡？
3. **科目優先序**：先做哪一科？（建議數學或理化）
4. **教科書版本**：需要支援哪幾家？（康軒/翰林/南一）只要一家可省下大量對照表工作。
5. **使用規模**：內部幾位老師自用，還是要開放對外註冊？（影響部署規格與權限設計）
6. **是否需要學生端**：只出紙本卷，還是也要線上作答？
7. **預算**：VLM 擷取的每頁成本可接受範圍？（決定用旗艦模型全跑，還是低成本模型初篩＋分級升級）
8. **答案從哪裡來**（PoC #001 發現的缺口）：你手上的考卷有幾成附答案卷？沒有答案的題目對老師價值極低，若多數卷缺答案，就必須把「AI 產生參考答案 + 人工核對」排進 MVP，而不是列為選配。
